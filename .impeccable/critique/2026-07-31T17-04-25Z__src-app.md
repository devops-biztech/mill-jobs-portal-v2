## Design Specificity Verdict

**LLM assessment**: Authored at the data/access-model layer, generic at the visual-expression layer. The domain modeling is real — actual mill codes, per-mill access scoping enforced server-side and verified live (a non-admin user is redirected out of `/admin/users`), an AWS sync pipeline, authentic lumber-mill job titles in the data ("Plant Laborer," "Log scaler," "Boiler/Kiln operator"). But the chrome — briefcase icon, "Jobs Portal Admin," three stat cards, an area chart, a bar chart, a data table — is interchangeable with a template for reviewing support tickets or orders at any multi-location company. Mill codes are never expanded to real names anywhere, so even the one distinctly domain-specific signal in the UI stays opaque to anyone outside the team.

**Deterministic scan**: The static source scanner (`detect.mjs` over `src/`) returned a clean `[]` — it inspects `.tsx/.ts/.css` text for literal anti-pattern signatures, and this codebase's source doesn't trip any of them. That's a different test than the rendered-DOM browser detector, which found real, render-time issues on every one of the 5 surfaces: `nested-cards` (visually confirmed via the injected overlay — concentric bordered Card containers, worst on Overview and the Detail page), `cramped-padding` on rounded containers (Applications, Users), and a synthetic `layout-transition` on width/height on every page (2 instances each — animating layout-affecting properties instead of `transform`, a real but minor perf/motion smell, likely from a shared hover/focus transition utility). Two detector hits read as false positives for this app specifically: `overused-font` ("open sans 95–99% of text") is the expected, by-design result of a deliberate Poppins-headings/Open-Sans-body pairing, not monotony; `em-dash-overuse` (13 em-dashes on the Detail page) is almost certainly applicant-submitted free text, not authored UI copy.

**Visual overlays**: Browser visualization ran via Playwright script (not a persistent human-visible tab in this session), so there's no live `[Human]` overlay to hand back to you right now — the injected detector's on-page overlay and console findings were captured and screenshotted by the sub-agent instead (saved under the scratchpad directory). ## Overall Impression

The bones are good — real per-mill access control that's actually enforced server-side, a thoughtful "recent vs. full history" default, and a clean, consistent navy/sky visual system that passes contrast checks in both themes. What's missing is polish at the exact points where an HR reviewer spends the most repeated time: the search bar can silently lie to you, the Applications table can't be sorted or bulk-actioned, and the Applicant Detail page — the page opened dozens of times a day — presents 40+ fields with zero hierarchy. The single biggest opportunity is fixing the search/duplicate-data trust gap first: an HR tool that might silently say "never applied" about someone who did is a compliance risk, not just a UX rough edge.

## What's Working

1. **Access scoping is real, not implied.** Verified live: a TRL/SRM-scoped user hitting `/admin/users` directly gets server-redirected to `/admin`, and the "Users" nav item never renders for non-admins. For a multi-tenant HR tool this is the trust guarantee everything else depends on, and it holds.
2. **The recent/full-history toggle is a good default, well-executed.** Hiding 955 of 1,259 records behind an explicit, dismissible "last 6 months" banner keeps the daily view fast while preserving one-click access to full history — the intent is right (the search gap below is the one place it leaks).
3. **The design-token layer is genuinely solid.** The navy/sky palette, Poppins/Open Sans pairing, and light/dark tokens hold up under measurement, not just eyeballing — computed contrast on muted text and status badges clears WCAG AA in both themes (light muted-fg ≈4.55–4.76:1, dark ≈6.96:1, badges ≈6.4–6.8:1).

## Priority Issues

**[P0] Search silently excludes results older than 6 months, producing false negatives**
- **Why it matters**: Searching for a real applicant who applied more than 6 months ago returns a flat "No applications found," with no hint that a time filter — not absence of data — caused it. For HR work, "did this person ever apply?" can be a compliance or rehire-eligibility question; a confident wrong answer here is worse than a slow right one.
- **Fix**: Either search the full dataset regardless of the recency toggle, or when a query returns 0 results within the recent window, automatically check the full dataset and surface "No matches in the last 6 months — 1 found in older applications. Show all?"
- **Suggested command**: `/impeccable harden`

**[P1] Company filter displays the literal string `"all"` instead of a label**
- **Why it matters**: Confirmed in every `/admin/applications` screenshot (both themes, both breakpoints): the filter trigger reads lowercase `all` instead of "All companies," inconsistent with the correctly-labeled "Select a mill" control elsewhere. This is the filter control opened dozens of times a day, and it reads as broken.
- **Fix**: Resolve the matched `SelectItem`'s label for the default value instead of falling back to the raw value string — check how `@base-ui/react`'s Select resolves `SelectValue` for a non-selected/default state on this version.
- **Suggested command**: `/impeccable polish`

**[P1] Duplicate application rows go unflagged, some with contradicting statuses**
- **Why it matters**: On page 1 of the Applications table alone, six applicants (Matthew Schoonover, Eric Sanchez, Donald Ross, Simon Vendrame, Donald Miller, Luke Anderson) each appear as back-to-back duplicate rows — Luke Anderson's pair even shows contradicting statuses (one Reviewed, one Pending) for what looks like the same submission. A reviewer risks double-contacting or missing a stale duplicate on the primary work surface.
- **Fix**: Dedupe by email + position + date-proximity at the query layer, or surface a "possible duplicate" indicator so pairs get resolved together.
- **Suggested command**: `/impeccable audit`

**[P1] Focus visibility is inconsistent, closing off keyboard and screen-reader users at several points**
- **Why it matters**: Independently confirmed from two angles. The "Sign in" submit button has no focus indicator at all when tabbed to (`outline: none`, zeroed `box-shadow`), while the adjacent inputs show one — a hard stop for a keyboard-only user on the very first screen. Separately: the sidebar sign-out button is icon-only with a `title` but no `aria-label` (announces only "button" to a screen reader); two non-interactive chart `<svg>` nodes absorb Tab focus on every Overview visit with no usable interaction; the 6 mill-access checkboxes aren't wrapped in a `fieldset`/`legend`, so a screen reader can't announce them as one related group; and Applicant Detail's 40+ field pairs render without a wrapping `<dl>`, flattening the semantic structure a screen-reader user relies on to navigate.
- **Fix**: Add a visible focus-visible style to all interactive elements including icon-only buttons and Select/Dialog triggers; add `aria-label` to icon-only controls; make decorative chart SVGs `aria-hidden`/`tabIndex={-1}`; wrap the mill-access checkbox group in `fieldset`/`legend`; wrap Detail-page field lists in `dl`/`dt`/`dd`.
- **Suggested command**: `/impeccable audit`

**[P2] Applicant Detail page has no visual hierarchy or progressive disclosure**
- **Why it matters**: 40+ fields render with identical uppercase-label/same-weight styling regardless of importance, and fully-empty sections (College 1/2, Trade School, License — all "—" for a high-school-only applicant) render in full rather than collapsing. The rendered-DOM detector corroborates this independently: 5 `nested-cards` hits on this page, the most of any surface, compounding the flat-field problem with literal nested chrome. This is the page opened most often in a review session, and it's the most tiring one to scan.
- **Fix**: Add a compact "at-a-glance" summary above the fold (name, position, company, contact, experience) and collapse/hide sections where every field is empty.
- **Suggested command**: `/impeccable layout`

## Persona Red Flags

**Alex (Power User)**: Can't sort the Applications table by Submitted date or Status — must scan each 25-row page manually. No bulk "mark reviewed," so clearing a routine queue is one row at a time via right-click even across 1,259 records. The six duplicate-row pairs on page 1 alone waste scanning time reviewing what looks like the same person twice. Searching for a name outside the default 6-month window returns nothing with no explanation — under time pressure, Alex trusts the empty result and wrongly concludes "never applied."

**Sam (Accessibility-Dependent User)**: Tabbing to "Sign in" on the very first screen produces no visible focus ring — confirmed via computed style, not a hunch. The sidebar sign-out control has no accessible name beyond "button." Two chart SVGs on the Overview page are dead stops in the tab order every single visit. The 6 mill-access checkboxes and the 40+ Detail-page field pairs both lack the semantic grouping (`fieldset`/`dl`) a screen reader depends on to convey "these belong together."

**Jordan (First-Timer)**: TRL/SRM/SLI/NFL/STLC/GL appear unexplained everywhere — sidebar footer, every table's Company column, the Users mill-access grid — with no legend or tooltip. "Sync from AWS" means nothing without context. The Applications page hides 76% of all records by default behind a small banner Jordan may not register, risking an incorrect read of total volume. There's no help affordance anywhere in the product.

## Minor Observations

- Applicant names are inconsistently cased ("DANIEL SMITH" next to "Justin Chartrand"), breaking row rhythm in both the Pending and Applications tables.
- A failed AWS sync surfaces the raw `error.message` directly in the toast — risk of leaking a technical message to a non-technical user with no next step.
- One Contact cell reads "Not Given" while every other missing value in the app uses "—" — an unintentional copy inconsistency.
- The clearing-the-queue empty state ("No applications are currently pending review.") is correct but emotionally flat for what's naturally an "inbox zero" moment.
- The trend chart's draw-in animation (~1–2s, no skeleton) can read as "no data" on a quick glance right after load — separate from, and in addition to, the stuck-open tooltip bug.
- Detector-confirmed, low-priority: a synthetic width/height `layout-transition` fires on every page (2 instances each), likely a shared hover/focus transition animating a layout property instead of `transform` — a minor perf/jank smell worth a look, not a redesign.
- Detector-confirmed, likely false positives for this app specifically: `overused-font` (open sans 95–99% of text) reflects the deliberate Poppins-headings/Open-Sans-body pairing working as intended, not monotony; `em-dash-overuse` on the Detail page is almost certainly applicant-submitted free text, not authored copy.
- `cramped-padding` flagged on rounded containers in Applications and Users — worth a quick visual check, pairs with the Aesthetic/Minimalist score of 3/4 rather than 4/4.
